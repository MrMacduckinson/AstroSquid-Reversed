ASTROSQUID 1.1: HOW THE FULL CAMPAIGN WAS ENABLED
Original PowerPC disassembly, reconstructed pseudocode and both port approaches
2026-11-04 — English technical handoff

1. THE IMPORTANT DISTINCTION

Our reconstruction and Sam's port do NOT unlock the campaign in the same way.

Our reconstruction starts a clean profile with valid registration state and a
valid name/code pair. The shareware test and reminder still exist in its source.
Sam's generator instead replaces the call to the shareware reminder with a NOP
before translating PowerPC into C. It leaves the registration flag unchanged,
which is why his menu can still say "Unregistered" while later levels are playable.

Neither mechanism means every stage-selection button is visible on a fresh
profile. Registration entitlement and saved campaign progress are separate.
The game has eight numbered levels, normally split into A/B sections, plus its
final encounter; our campaign data contains 17 stage files. The shareware barrier
is after the six ordinary sections of levels 1-3, before section 4A.

2. EVIDENCE AND ADDRESS CONVENTIONS

The original input is FCOD resource 1001 (FB^3.PPC) from the same game revision
used by the selected original download and Sam's archive. Its SHA-256 is:
eadd946129a4cb8e0b5b5511863e11cb938de06c96677f4c364f31f8dd46371f

The FCOD slice beginning at its PEF header (FCOD offset0x40, including any
trailing data in that resource) has SHA-256:
dd748d51e3591ddf5545857cd6b978aa29cc67d7470b1f4bd9c167e4ce5ecd20

Sam's extracted AstroSquid_code.pef is normalized for analysis: its header extends
the code section to include linker glue and it omits trailing resource data. It
is not byte-identical to that whole FCOD slice. The code-plus-glue byte range
PEF offsets0x80..0x69D04 was verified identical in both representations. All
instruction comparisons below use the original FCOD bytes, not a patched export.

Original function ranges, as CODE-SECTION OFFSETS, with exclusive end addresses:
  CHECKREGCODE  0x03D844 .. 0x03DD90  (1356 bytes)
  REGREMINDER   0x03E924 .. 0x03EB1C  (504 bytes)
  GETREADY      0x04E004 .. 0x04E9B0  (2476 bytes)

A number such as0x04E998 below is NOT an offset into the whole .rsrc, ZIP or
Macintosh application. The code section begins at PEF file offset0x80.
The call is therefore at PEF file offset0x04EA18, or FCOD payload offset0x04EA58.
The resource container has another offset layer; do not apply those offsets to
an entire file without parsing it. Sam uses virtual CODE_BASE0x00100000, so the
same instruction is at modeled address0x0014E998. This is not a claimed G5 load
address, and it is not an offset in the new x86_64 executable.

The original saved assembly is in Sam's decompiled/code/03_game.s. Every machine
word reproduced in the three listings below was freshly checked against the
original PEF bytes: 493 instructions total. Symbol/variable interpretations
come from the saved analysis and matching reconstructed source.

REA was attempted for fresh native analysis, but its open_binary tool rejected
the legacy PEF format as unsupported. No fresh REA/Ghidra decompilation is claimed.
The readable C below is a reconstructed semantic explanation. The actual
machine-word listings and the saved/generated C are identified separately.

  r14+0x0A0C: signed16 registration flag (zero means unregistered)
  r14+0x0A82: signed16 numbered level
  r14+0x0A84: signed16 section/half (A=1, B=2)

Readable semantic decompilation of this block:

  int registered = read_s16(globals + 0x0A0C);
  int level      = read_s16(globals + 0x0A82);
  int half       = read_s16(globals + 0x0A84);
  int section    = (level - 1) * 2 + half;
  if (registered == 0 && section > 6) {
      REGREMINDER();
  }

FutureBASIC represents a true comparison with -1 (all bits set), not necessarily
C's integer1. The first sequence builds (registered==0) as0/-1 inr31. The second
builds (section>6) as0/-1. and. combines them and updates the condition register.
At0x04E990, bne takes the nonzero result to the call at0x04E998.

The order of cmpw at0x04E978 matters: it compares6 against section. bge skips the
true assignment when6>=section, so the resulting condition is section>6, not<6.

Boundary examples:
  level1, half1 -> section1: allowed even when unregistered
  level3, half2 -> section6: allowed even when unregistered
  level4, half1 -> section7: invokes REGREMINDER when unregistered
  level8, half2 -> section16: same barrier when unregistered
  any such section with a nonzero registration flag: no reminder call

There is no asset download or missing-level extraction at this gate. The later
content is already present; the conditional changes whether play may continue.

4. WHAT REGREMINDER DOES

Simplified semantic decompilation, omitting graphics argument plumbing:

  void REGREMINDER(void) {
      set_2d_projection_and_640x480_viewport();
      clear_color_buffer();
      draw_picture(70, 0, 0, 640, 480);  // registration reminder artwork
      swap_buffers();
      delay(5000);                      // _DODELAY argument0x1388
      do {
          service_music();
          read_key_map();
      } while (!mouse_button() && !fire_control());
      write_s16(globals + 0x0A68, 0);
      write_s16(globals + 0x058C, 1);    // requests ending this play session
  }

The last two state writes explain why the call is consequential: it does not
merely draw a harmless label and continue normal play. Our matching host method
clears paused and sets gameEndRequested after the reminder. The raw original
state offsets and store instructions appear in Appendix A.

5. SAM'S ONE-INSTRUCTION CHANGE

Sam's port/tools/recompile.py contains this existing patch entry:

  0x04e998: (0x4BFEFF8D, 0x60000000,
             'GETREADY: skip the shareware REGREMINDER (bl -> nop)')

Before, original big-endian bytes:
  4B FE FF 8D    bl 0x03E924          ; REGREMINDER
After, in the translator's temporary code buffer:
  60 00 00 00    ori r0,r0,0          ; canonical PowerPC nop

The branch displacement is -0x10074:
  0x04E998 - 0x10074 = 0x03E924.
Its link bit is set, so the original instruction also writes the return address
to LR. Replacing it removes that call. GETREADY's normal epilogue subsequently
restores its saved caller LR; a dummy function call is not needed.

The generator checks that the old word is exactly0x4BFEFF8D before replacing it;
otherwise it aborts rather than patching an unrelated revision. It then translates
the patched in-memory code into C. The raw resource fork is written before that
patch loop, so a raw resource file can still contain the ORIGINAL call while the
compiled generated C already omits it. The original ZIP is not modified.

Actual generated C in port/gen/ppc_code_06.c:

  L_04e988: c->r[3] = c->r[31] & c->r[3]; SET_CR0(c, c->r[3]);
            c->r[3] = c->r[3] | c->r[3]; SET_CR0(c, c->r[3]);
            if (!(c->cr[0] & 2)) goto L_04e998;
  L_04e994: goto L_04e99c;
  L_04e998: c->r[0] = c->r[0] | 0x00000000u;
  L_04e99c: c->r[1] = c->r[1] + 0x000000d0u;

The self-OR is the translated NOP, not an accidental missing operation. Condition
calculation remains, but either branch now reaches the epilogue without calling
REGREMINDER. No registration key is computed by this patch. Registration/menu
labels and progress-selection state are left alone.

This was already present in Sam's submitted archive. Our later Intel10.7 build
adaptation did not introduce it or modify the generator/generated game code.

6. OUR RECONSTRUCTION: VALID REGISTRATION, NOT THAT NOP

Current src/preview.m initializes a clean launch with:

  ui.registered = YES;
  ui.registeredName = @"MACSPB";
  registeredSerial = @"UACHCUFD";

The Tiger counterpart uses the same registration values. The original-inspired
barrier remains in advanceFlowWithKey: at the ready-to-play transition:

  if (!ui.registered && (flow.stage-1)*2 + flow.half > 6)
      [self showRegistrationReminder];

It does not fire for the registered clean-profile defaults. This is not a blanket
always-true replacement of the validator. Saved registration dictionaries and
packed preferences can override those startup defaults and are validated. An
invalid stored registration can therefore restore unregistered behavior. We did
not silently erase existing profiles to force the state on every launch.

The name/code pair is not an SSH password, server token, account credential or
Graphing Calculator serial. It belongs to AstroSquid's local registration scheme.
The supplied startup code agrees with the reconstructed original validator.

7. RECONSTRUCTED CHECKREGCODE VALIDATOR

CHECKREGCODE starts at code offset0x03D844. The original routine uses Pascal-string
helpers, modular arithmetic, character construction and a final string comparison.
For example,0x03D898..0x03D8AC takes the name length, multiplies it by128, divides
by26 and subtracts the quotient product: the remainder modulo26. Later blocks
use selected name bytes with multipliers13,42,35,24,72,11. Appendix B includes the
entire byte-verified function, including its UI/state handling.

The following is the concise existing C reconstruction of the validation result,
not a verbatim output from a new decompiler and not all of the function's UI side
effects. It uses raw name bytes (the host supplies MacRoman), not UTF-8 character
counts or an invented uppercase/name-normalization step:

int astro_registration_valid(const unsigned char *name,size_t length,const unsigned char *code,size_t code_length){
    if(length>255||(!name&&length)||!code||code_length!=8)return 0;
    unsigned first=length?name[0]:0,second=length>1?name[1]:0,third=length>2?name[2]:0;
    unsigned penultimate=length?name[length>1?length-2:0]:0;
    unsigned p=penultimate*42%26,q=second*35%26,r=third*24%26,t=third*11%26;
    unsigned a=(length*128%26+p)%26,b=(q+a)%26,c=(q+b)%26;
    unsigned digits[]={a,(first*13%26+q)%26,(p+r)%26,b,(first*72%26+r)%26,c,(r+t)%26,(t+c)%26};
    unsigned char expected[8];for(unsigned i=0;i<8;i++)expected[i]='A'+digits[i];
    return memcmp(code,expected,8)==0;
}

For the shipped name MACSPB:
  bytes = [77,65,67,83,80,66], length=6
  first=77, second=65, third=67, penultimate=80
  p=(80*42)%26=6; q=(65*35)%26=13
  r=(67*24)%26=22; t=(67*11)%26=9
  a=(6*128+6)%26=20; b=(13+20)%26=7; c=(13+7)%26=20
  output indices = [20,0,2,7,2,20,5,3]
  add ASCII 'A' -> UACHCUFD

The original/host validator regression was rerun while preparing this document:
12,288 saved-original cases matched exactly, including computed comparison
operands. Cases cover name lengths0..255, three byte patterns, altered/case-changed/
short/long/zero-containing codes and both prior-state values. This supports the
reconstructed validator; it is not a new full-game or all-GPU validation.

8. CAMPAIGN ENTITLEMENT VS THE LEVEL-SELECTION MENU

Our ui.unlockedLevel starts at least1, loads stored progression, and advances:

  ui.unlockedLevel = MAX(ui.unlockedLevel,
      MIN(16, (campaign.level-1)*2 + campaign.half));

The menu enables LevelN only when N>0 && N<=ui.unlockedLevel. Thus a fresh registered
profile can progress past level3 without displaying every later-stage shortcut
immediately. The 17th campaign file/final encounter is not proof of a Level17
shortcut; this selection counter is capped at16.

The packed preference record is542 bytes. Its progression word is at offset534,
and disk encoding adds100 when saving and subtracts100 when loading. Registration
strings occupy separate Pascal-string slots at offsets10 and266. The progression
encoding is not the registration algorithm and changing it is not how we removed
the shareware barrier. Neither implementation needs new level assets to enable
continued play.
